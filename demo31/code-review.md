# 代码 CR Skill

## 基本信息
- **名称**：代码 CR
- **触发词**：CR、code review、代码审查、review
- **描述**：对当前分支与 master 的差异进行技术与业务双重审查，输出问题清单及修复建议，自动关联 PRD/技术文档并按严重程度分级。

## 工作流程

### 1. 前置询问
在执行审查前，必须先向用户询问以下信息：
- PRD 文档的 URL（可多个，逗号分隔，或直接粘贴内容）
- 后端技术设计文档的 URL（可多个，逗号分隔，或直接粘贴内容）
- 自定义 CheckList（可选，若不提供则使用内置技术检查清单）
- 本次改动的目标功能模块（可选，若不提供则根据文档与 diff 自动识别）

用户回复后，方可继续。

### 2. 获取代码差异
假设当前工作目录为 Git 仓库根目录。
执行命令：`git diff master...HEAD`（或 `git diff master...当前分支名`）获取完整差异。
若 diff 过大（超过 500 行或文件数超过 20），提醒用户可指定子目录或文件范围缩小审查范围。

### 3. 解析业务文档
从用户提供的 URL 抓取 PRD 与技术设计文档内容（若无法直接访问，请用户粘贴文本）。
扫描本地项目 `/knowledge` 目录，如有相关架构说明、领域模型等文档，一并作为业务审查依据。

### 4. 技术性审查
基于 diff 内容，按以下内置检查清单逐项扫描（不限于此，可根据语言特性扩展）：
- 空指针 / 空引用 / nil 处理
- 资源泄露（文件句柄、数据库连接、网络连接、锁等未释放）
- 并发问题（竞态条件、死锁、线程安全、原子性）
- 性能问题（不必要的循环、N+1 查询、大对象拷贝、无索引的数据库操作、内存泄漏）
- 异常处理（捕获过于宽泛、吞异常、未处理受检异常）
- 事务边界与一致性
- 安全漏洞（SQL 注入、XSS、越权、敏感信息泄露、不安全的反序列化）
- API 兼容性（破坏性变更、接口签名修改未同步）
- 边界条件与输入校验
- 日志与监控（缺失关键日志、敏感信息打印）
- 代码风格与可维护性（重复代码、过长方法、圈复杂度过高）
- 依赖与配置（版本冲突、硬编码、环境差异）

### 5. 业务性审查

#### 5.1 提取整体业务串联图

从 PRD、技术设计文档和本地 /knowledge 知识库中，提取该需求在整体业务系统中的定位与上下游依赖。

构建或更新业务流程图/系统交互图（可用文字描述或 Mermaid 代码），展示涉及的角色、系统、模块、关键交互及数据流向。

识别与本次改动相关的核心业务链路、状态流转、外部系统依赖，以及可能受影响的现有功能。

**目的**：从全局视角理解本次改动的影响范围，避免只聚焦局部而忽略全局影响。

#### 5.2 提取业务规则与用例

从 PRD 和技术设计文档中提取：

- **整体串联业务图**：
- **用户故事/功能点**：如“用户下单后扣减库存”、“超时未支付自动取消订单”。
- **关键业务规则**：如状态机（订单状态流转）、权限控制、金额精度（BigDecimal 使用）、幂等要求（重复提交处理）、校验规则（参数合法性）、超时/重试策略等。
- **核心流程**：如支付流程、退款流程、审批流等。

#### 5.3 识别入口点

从 diff 中识别所有业务入口：

- Controller 接口（REST/RPC）
- 定时任务（@Scheduled、XXL-Job 等）
- 消息队列消费者（MQ listener）
- 事件监听器（Spring Event、Guava EventBus 等）
- 其他触发方式（如命令行、回调接口）

#### 5.4 沿调用链逐层审查

对每个入口，沿调用链向下追踪（例如 Controller → Service → Repository/外部依赖），逐层核对：

- 入口层：参数校验、权限验证、幂等控制、返回值结构是否符合 API 定义。
- 业务层：核心业务逻辑是否与 PRD、技术方案 一致，状态流转是否正确，异常分支是否覆盖。
- 数据层：数据模型是否与技术设计一致，事务边界、乐观锁/悲观锁使用是否正确。
- 外部依赖：调用第三方/中间件时是否处理了超时、重试、降级，是否影响业务一致性。

#### 5.5 业务规则逐项验证

将一些关键的业务规则、业务字段作为检查项，在代码中寻找对应实现并验证

> 以下举一些关键业务规则，关键业务字段的例子：
> 
> - 比如状态机：是否所有合法状态转换都有代码路径，非法转换是否被阻止。
> - 比如幂等性：是否有唯一键/Token/Redis 锁等机制。
> - 比如数据流分析：关注关键数据（如订单金额、库存数量）从入口到持久化的过程中是否被正确传递和转换。


### 6. 问题分级
- **P0（阻塞）**：服务不可用或核心能力瘫痪，必须立即处理。例如：
  - 启动即崩溃、死锁导致请求无响应
  - 数据丢失或严重数据错误
  - 安全漏洞可直接被利用造成重大损失

- **P1（高优先级）**：主要功能受损或大范围用户受影响，需要高优先级修复。例如：
  - 核心流程在特定条件下失败
  - 性能回退导致接口超时
  - 业务规则错误导致资金/状态异常

- **P2（可延后/建议）**：有明确影响但可绕过、可延后、风险可控。例如：
  - 非核心功能的 bug
  - 代码可读性差但不影响运行
  - 资源未释放但暂不泄露（如低频调用）
  - 优化建议（如缓存策略、日志补充）

### 7. 输出报告格式
以 Markdown 格式输出，报告整体采用表格呈现关键信息，问题清单按严重程度降序排列。

#### 7.1 关联信息表
| 项目             | 内容                   |
|------------------|------------------------|
| 需求名称         | <从 PRD 提取>          |
| PRD 链接         | <URL>                  |
| 技术设计文档链接 | <URL>                  |
| 审查分支         | <当前分支名> vs master |
| 审查时间         | <自动生成>             |

#### 7.2 变更概览表
| 指标         | 数值               |
|--------------|--------------------|
| 变更文件数   | X                  |
| 新增行数     | X                  |
| 删除行数     | X                  |
| 涉及功能模块 | <列表，用逗号分隔> |

#### 7.3 问题清单表（按严重程度排序）
使用一个统一表格，每行一个问题，列定义如下：

| 编号 | 严重程度 | 问题标题   | 位置                    | 问题原因           | 修复建议                    | 示例代码                    |
|------|----------|------------|-------------------------|--------------------|-----------------------------|-----------------------------|
| P0-1 | P0       | 空指针风险 | src/UserService.java:45 | 未判空直接调用方法 | 增加空值判断或使用 Optional | `if (user != null) { ... }` |

严重程度顺序：P0 → P1 → P2。
示例代码使用简短片段，若需多行可用 `<br>` 换行或引用外部代码块。
若某类问题为空，可省略该严重程度行，或注明"无"。

#### 7.4 业务审查结论表
| 项目             | 内容               |

| 与设计文档不一致 | <列表，用逗号分隔> |

#### 7.5 总结
一段话总体评价及风险提示（可继续使用段落文本）。

### 8. 注意事项
- 若用户未提供 PRD/技术文档，则业务审查部分仅基于本地 `/knowledge` 目录和 diff 内容进行推断，并提醒用户可能不完整。
- 修复建议中的示例代码片段应尽量简洁，只展示关键部分。
- 对每个问题给出唯一编号（P0-1, P1-2 等），方便后续跟踪。
- 若 diff 无内容，提示用户当前分支与 master 无差异。
